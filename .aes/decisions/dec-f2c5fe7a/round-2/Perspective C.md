The missing directions are about distribution and incentives. MCP connectivity makes UniView accessible; it does not make agents choose it.

**1. Deliver a portable “review receipt” for agent-produced files.** Start with one compelling handoff: an agent produces a spreadsheet, PDF or report; UniView opens it alongside source references, differences, annotations and reproducible previews. Offer a tiny SDK and integrations that make this handoff one call. Keep the receipt format open so users retain their review history.

**Trade-offs:** Reliable previews and provenance require investment. A receipt must distinguish recorded claims from independently checked results. Monetize shared review, organizational retention and policy controls; preserve free local viewing.

**2. Let existing tools become plugins without rewrites.** Provide adapters for established CLI converters, libraries and local services. Run native dependencies in separately isolated desktop workers; phones consume previews or delegate explicitly to a paired computer.

**Trade-offs:** Faster useful coverage, but packaging, licensing and worker isolation become substantial responsibilities. Declare execution location and transferred data clearly. Cross-device convenience must never silently expand file access.

**3. Build a demand-funded format exchange.** Let users attach sanitized fixtures and bounties to missing formats or actions. Give developers conformance tests, usage signals and maintenance funding.

**Trade-offs:** Demand becomes concrete, but private samples, incompatible licenses, abandoned plugins and gaming require governance. Charge for funded delivery and support rather than basic publishing.

**I rank option 1 first:** it supplies a repeated reason for both agents and users to choose UniView before a marketplace exists. Measure repeat review sessions and integration retention—not plugin counts. Sandboxing remains foundational; signatures establish provenance, not safety.
